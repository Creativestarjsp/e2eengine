# Deciding Whether to Illustrate

## The questions

Answer these from the screen and the user's goal. Do not put them to the user unless the request is genuinely ambiguous.

1. Does the user need visual explanation?
2. Would an illustration improve comprehension?
3. Would it communicate the concept faster than text?
4. Does the screen benefit from emotional or visual engagement?
5. Is there sufficient space?
6. Does it support the primary user task?
7. Would it improve an empty, onboarding, success, error, or marketing experience?
8. Does an illustration fit the product's visual language?
9. Could an icon communicate the same idea more effectively?
10. Would it distract from the primary action or content?

A "yes" to 9 or 10 usually means no illustration.

## Where illustrations earn their place

| Context | Examples | Guidance |
| --- | --- | --- |
| Empty states | No projects, messages, notifications, saved items, transactions, team members | Makes an empty view informative and friendly |
| Onboarding | Welcome, product introduction, first project, feature introduction | Visual storytelling of the product experience |
| Success | Payment successful, account created, order completed, submission sent | Positive but restrained |
| Error | Connection failed, page unavailable, upload failed, server error | Friendly, without creating anxiety |
| No results | Search or filter returned nothing | Only when it helps explain the state |
| Marketing and hero sections | Landing pages, feature sections, product storytelling | May be more detailed than UI-state artwork |
| Educational content | Concepts, processes, tutorials, step-by-step workflows | When the picture explains what words cannot |

Product types this covers: web applications, SaaS products, dashboards, mobile applications, landing pages, admin applications, educational interfaces, and product marketing.

## Where they do not

Do not illustrate merely because there is empty space. Avoid illustrations in:

- sign-in and registration forms
- settings and configuration screens
- dense admin, CRUD, and data-table views
- financial transaction screens
- developer tools and monitoring dashboards
- dense analytics interfaces
- small mobile screens where the artwork would push content down
- navigation
- simple confirmation dialogs and action buttons

Use the lightest thing that works:

- If an icon is sufficient, use an icon.
- If typography is sufficient, use typography.
- If whitespace is sufficient, use whitespace.
- If the content is data, use a chart.

## Icon or illustration

| Use an icon when the concept is | Use an illustration when the concept benefits from |
| --- | --- |
| simple, immediate, symbolic, action-oriented | context, storytelling, characters, several objects, emotion, an environment, visual explanation |
| Delete, Edit, Search, Settings, Lock, Download, Upload, Add, Close, Warning | "No projects yet", "Welcome to your workspace", "Your order has been delivered", "Nothing found", "Complete your profile", "Your team is ready" |

## Reuse before generating

1. Does the project already contain a suitable illustration?
2. Can an existing design-system asset be reused?
3. Can an existing illustration be adapted safely?
4. Is a simple icon sufficient?
5. Only then generate a new one.
